The graded artifact isn't the best recommender — it's the agent that builds one cheaply, autonomously, and without falling over. Every design choice below is aimed at a scoring lever.

01 — The idea

Two layers, stacked

A recommender pipeline is the thing being optimized. An LLM-driven loop is the thing doing the optimizing. You build the outer loop; it writes and rewrites the inner pipeline on KuaiRand-Pure, chasing NDCG@10 / Recall@50 on the click label — using only train + validation, never the hidden test.

The loop writes the pipeline. Purple stages reason; teal stages execute.
02 — Layer one · the pipeline

What a good run climbs through

The agent generates this code — you don't write it by hand. But the proposer needs to be steered toward a trajectory like this, where gains come from the whole stack, not just swapping the model.

Reproduce the baseline

Stand up an end-to-end pipeline — load the fixed date splits, embed user/item IDs, a simple ranker — and confirm it matches the organizer's reported score. One clean turn of the loop.

Feature engineering

User-history sequences, temporal/recency features (the splits are date-based), feature crossing like user × category. Often the cheapest wins on the board.

Architecture

Climb from a DeepFM-style start toward attention over user history (DIN) or explicit interactions (DCNv2).

Multi-task learningthe KuaiRand insight

Only click is scored, but there are 12 feedback signals. An MMoE / PLE head that also predicts like, long_view, and follow shares representation and lifts the click metric — PLE directly targets the seesaw problem.

Training strategy

Negative sampling, loss choice, LR schedule. If the agent gets ambitious, the randomized-exposure data opens a debiasing angle.

Score the converged result, not the peak. A run converges when validation stops improving by more than ε over N iterations, or the budget runs out. Designate the converged validation-best checkpoint as final — don't chase a lucky mid-run high.
03 — Layer two · the agent

The parts of the loop

Robustness, autonomy, and the run logs are all graded on how this harness behaves — so instrument it heavily rather than treating these parts as plumbing.

Reasoning

Proposer

Reads the current best solution plus the history of what's been tried, and picks the next move — grounded in named RS methods, since that's exactly what Innovation scoring rewards.

Execution

Coder

Turns the chosen idea into a concrete code diff — or, with a config-driven library, a config edit, which is cheaper and less error-prone.

Execution

Executor

Runs training + eval in a sandbox with a hard timeout, capturing both metrics and any stack traces.

Reasoning

Evaluator

Reads the validation score, updates the solution tree, and applies the ε / N rule to decide keep-going vs. converged.

Error handling

Debugger

Your robustness story: on an error or timeout, feed the message back to the LLM to patch and retry, so a human never has to unstick it.

Storage

Solution tree / memory

Holds every attempt and its score, so promising branches get reused and dead ones get pruned.

Storage

Run logger

One structured record per iteration — hypothesis, diff, metrics, error/recovery. Not polish: it's a required deliverable and the judges' evidence for autonomy and robustness.

04 — Strategy

Design to the scoring levers

The rubric tells you what to optimize. Most teams over-index on the score and leave the other 65% on the table.

Technical Execution35%

Beat the baseline on hidden test — and recover from failures. Robustness is judged by how you handle a crash, not whether one happens. Log the crash-and-recover; a suspiciously clean run scores worse.

Innovation & Insight20%

Judged on what the agent chose and why. The multi-task angle on the 12 signals is your ready-made insight — non-obvious and grounded in the domain.

Impact & Relevance20%

Autonomy, measured by intervention count. Every spot a human would step in is a gap for the debugger and convergence logic to cover. Track the number — you report it.

Feasibility & Practicality15%

Tokens + GPU-hours. Route routine coding to a cheap model, explore on a subsample and promote survivors, early-stop bad runs. A cheaper agent at the same score wins.

Presentation10% · final only

Final event only — but the run logs and solution-tree visualization do double duty as the story.

06 — Bonus · scaling to 27k

Same brain, bigger muscles

The loop is untouched — it's dataset-agnostic. What breaks at 27k is the economics: 322M interactions is ~230× Pure, so one full-data run that took minutes now takes hours, and an agent built on many cheap iterations stalls. Everything below restores cheap iteration and survives long runs.

The one conceptual change: give the loop two eval fidelities. The agent explores ideas on a cheap proxy and promotes only the survivors to full 27k — and Pure and 1k are ready-made proxies, since they're the same task on smaller data.

Ideas explored cheaply; only survivors are promoted. The solution tree stores each idea's score at every fidelity.
Execution · data

Cached columnar data

322M rows won't sit in pandas. Convert to Parquet, load with Polars/DuckDB streaming, and precompute ID encodings and user-history sequences once — recomputing features per iteration is a silent budget killer.

Execution

Executor at scale

bf16 / mixed precision, large batches, multi-GPU DDP if you have the cards. Most important: checkpoint + resume, so a crash at hour 2.5 becomes a resume, not a lost run.

Error handling

OOM-aware debugger

Add one failure mode explicitly: out-of-memory is the most common failure at scale and the easiest to recover — catch it, halve the batch, retry. A concrete logged win for robustness.

Reasoning

Explore cheap, confirm expensive

Rank ideas on the subsample / Pure / 1k tiers, promote only survivors to full 27k (Optuna pruning makes it finishable). Since 27k is bonus and GPU-hours are scored, spend most iterations cheap and reserve 27k for a handful of confirmations.

TorchRec isn't actually required here. Sharded embeddings solve table size (cardinality), but with only ~27K users and a modest item catalog your tables fit on one GPU — the bottleneck is interaction throughput. FuxiCTR + DDP + AMP is simpler for the agent to iterate on; reach for TorchRec only if throughput is still the wall after that.
07 — If you build one thing

The recommended stack

fork AIDE→ drive FuxiCTR configs→ Optuna pruning + LiteLLM routing→ log to MLflow

The harness handles autonomy and robustness, FuxiCTR gives the agent a config surface to iterate on, pruning and routing keep the cost score down, and MLflow produces the required logs. All four scored levers, one stack.
